# BigWork

Консольный проект на .NET 10: библиотека с обобщёнными классами, интерфейсами и методами расширения, а в программе — примеры на товарах и клиентах.

## Ответы на вопросы

### Шаг 0. Решение и проекты

1. **Зачем два проекта?** В `BigWork.Core` лежит общая логика, в `BigWork` — пример её использования. Библиотеку можно подключить и к другой программе.
2. **Если убрать ссылку на библиотеку?** Консольный проект перестанет видеть её типы, и сборка не пройдёт.
3. **Почему библиотека не запускается?** У неё нет точки входа. `BigWork` — консольное приложение с `Program.cs`.

### Шаг 1. `Buffer<T>`

1. **`protected`, `private`, `public` для `items`:** `protected` даёт доступ наследникам. `private` скрыл бы поле от них, а `public` позволил бы менять список откуда угодно.
2. **Что делает `readonly`?** Нельзя присвоить полю другой список после создания объекта. Добавлять элементы в сам список можно.
3. **Зачем `TryAdd` возвращает `bool`?** Наследник сможет отказать в добавлении и вернуть `false`, как это делает `GuardedBuffer<T>`.
4. **Без `virtual`?** `GuardedBuffer<T>` не смог бы переопределить метод через `override`.
5. **`new()` и `new List<T>()`:** Создают один и тот же список. В первом случае тип уже известен из объявления поля.

### Шаг 2. `LabeledBuffer`

1. **Фиксированный и открытый тип:** `LabeledBuffer` всегда хранит строки, а `GuardedBuffer<T>` работает с разными `T`.
2. **Почему `PrintAllUpper` не в `Buffer<T>`?** У произвольного `T` нет строкового метода `ToUpper()`.
3. **Можно ли создать `LabeledBuffer<int>`?** Нет: у `LabeledBuffer` нет параметра типа.
4. **Если наследоваться от `Buffer<object>`?** Числа хранить можно (с упаковкой `int`), но тогда элементы уже не гарантированно строки: перед `ToUpper()` пришлось бы проверять или приводить тип.

### Шаг 3. `GuardedBuffer<T>`

1. **Зачем проверять до `base.TryAdd`?** Чтобы отклонённое значение вообще не попало в список.
2. **Если увеличить счётчик до результата базы?** Он мог бы засчитать добавление, которое базовый метод не подтвердил.
3. **Разница между `int` и `string`:** Код класса один, но переданные проверки разные: числа должны быть положительными, строки — непустыми.
4. **Почему не вызвать `items.Add` напрямую?** Так обойдём логику `Buffer<T>.TryAdd` и его результат. Если база изменится, наследник начнёт вести себя иначе.
5. **Если зашить условие внутрь класса?** Проверка станет одной для всех экземпляров; передавать свои правила через конструктор уже не получится.

### Шаг 4. `Record<T>` и `Map`

1. **`struct` и `class`:** Структура — значимый тип: присваивание копирует значение. У класса копируется ссылка на объект.
2. **Без `ToString()`:** Вместо `°C: 20` вывелось бы имя типа записи.
3. **Откуда взялся `TResult = string`?** Во втором вызове лямбда возвращает строки `"тепло"` и `"холодно"`; компилятор вывел тип по ней.
4. **Почему не отдельные методы?** Написать их можно, но пришлось бы дублировать преобразование для каждого сочетания типов. Один `Map` принимает разные функции.
5. **Убрать `ToString()` — заметно?** Да: строки с температурой, категорией и здоровьем станут менее понятными — останется имя типа.

### Шаг 5. Контракты

1. **Если убрать `where T : IEntity`?** В `GetById` обращение к `item.Id` не скомпилируется: у произвольного `T` такого свойства может не быть.
2. **Почему проверка при компиляции?** Ограничение описывает допустимые типы заранее; неподходящий тип не должен дожить до запуска.
3. **Что значит `T?`?** Для ссылочного `T` результат может быть `null`. Для структуры в этом коде возвращается `default(T)`, а не обязательно `Nullable<T>`.
4. **Добавить `Put(T)` в `IContainer<out T>`?** Получим CS1961: `out T` разрешён на выходе, а параметр `Put` принимает его на вход.

### Шаг 6. Репозиторий

1. **Почему ограничение повторяется в реализации?** `IRepository<T>` принимает только `IEntity`, и самому классу тоже нужен доступ к `item.Id`.
2. **Что вернёт `default`?** Для ссылочного типа — `null`, для `int` — `0`. Сам `int` для этого репозитория не подходит, потому что не реализует `IEntity`.
3. **Почему не `return null`?** `T` может быть структурой; компилятор выдаст CS0403. `default` подходит обоим случаям.
4. **Почему `items` здесь `private`?** Репозиторию не нужно отдавать список наследникам. В `Buffer<T>` поле `protected` нужно для `LabeledBuffer`.

### Шаг 7. Ковариантность

1. **Почему интерфейс принимает `Dog`, а класс — нет?** В `IContainer<out T>` разрешена ковариантность, а `Container<T>` инвариантен.
2. **Цена `out T`:** Через такой интерфейс можно получать `T`, но нельзя принимать его в методе вроде `Put(T)`.
3. **Зачем `sealed`?** Он запрещает наследоваться от `Container<T>`. Ковариантность при этом обеспечена `out T` у интерфейса, а не словом `sealed`.
4. **Когда полезен `IContainer<Animal>`?** Метод, который только читает животное, примет и контейнер с собакой без копирования в `Container<Animal>`.

### Шаг 8. Методы расширения

1. **Если заменить `IEnumerable<T>` на `List<T>`?** Вызовы на списках останутся, а массивы и результаты LINQ-запросов уже не подойдут.
2. **Для чего `IComparable<T>`?** Без ограничения компилятор не разрешит вызов `item.CompareTo(...)` для неизвестного `T`.
3. **Почему не LINQ `Max()`?** Здесь нужно вернуть `default` и для пустого списка чисел. `Max()` для него выбросит исключение.
4. **`default` против `null`:** `default` допустим и для значимых типов; поэтому пустой `List<int>` даёт `0`, а пустой `List<string>` — `null`.
5. **Что делает `best!`?** Говорит анализатору, что перед сравнением значение уже найдено. Без `!` возможно предупреждение о `null`; сам оператор ничего не проверяет при запуске.

### Шаг 9. Предметные типы

1. **Убрать `Id` у `Product`?** Класс перестанет выполнять контракт `IEntity`, и репозиторий с `Product` не соберётся.
2. **Почему `Product?` в `CompareTo`?** На вход может прийти `null`; в коде этот случай отдельно обработан.
3. **Если всегда возвращать `1`?** Даже равные товары будут считаться неравными, а `FindMax` станет зависеть от порядка элементов вместо цены.
4. **Без `ToString()` у товара?** `PrintAll` выведет имя типа вместо названия и цены.
5. **Почему сравним только `Product`?** Для товара ищем максимум по цене; клиенты участвуют в поиске по `Id`, но сравнение им здесь не нужно.

### Шаг 10. Общий запуск

1. **Почему UTF-8 в начале?** Вывод с кириллицей начинается сразу, поэтому кодировку выставляем до первой строки.
2. **Чем подтверждается обобщённость `GuardedBuffer<T>`?** Одна реализация работает и с `int`, и со `string`, причём правила проверки у них разные.
3. **Где видна независимость счётчиков?** Для чисел `AcceptedCount = 2`, для строк `AcceptedCount = 1`.
4. **Где `double` превратился в `string`?** Строка `double → string: Категория: тепло`: тот же `Map` получил лямбду, возвращающую строку.
5. **Пустой `List<int>`:** В выводе `0`, потому что это `default(int)`. Это не ошибка и не обязательно найденный максимум.

### Шаг 11. Ожидаемые ошибки

1. **Почему CS0029 только у класса?** `Container<Dog>` нельзя присвоить `Container<Animal>`, но его можно рассматривать как `IContainer<Animal>` благодаря `out T`.
2. **Если заменить `out T` на `in T`?** `Put(T)` станет допустим, зато `GetItem(): T` уже нарушит правило вариативности.
3. **Какие ещё типы нельзя дать репозиторию?** Например, `Dog` и `int`: они не реализуют `IEntity`.
4. **Почему ошибки найдены до запуска?** Несовместимые типы и ограничения проверяются компилятором по объявлениям классов и интерфейсов.
5. **Чем это полезно?** Ошибку видно сразу при сборке, а не после запуска и поиска причины в выводе программы.

### Шаг 12. Проверка

У этого шага отдельных вопросов нет. Release-сборка решения прошла без ошибок и предупреждений; программа выводит все блоки A–D. Скриншоты ожидаемых ошибок в README не приложены.
